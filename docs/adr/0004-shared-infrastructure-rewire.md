# ADR-0004: Rewire onto shared/real infrastructure (regulatory-tracker, dcs, real CFD, crm.pipeline, murakumo-main LLM)

## Status

Accepted. REFACTOR pass only — swaps bespoke internal implementations for shared/real infrastructure while preserving the external contract (all 11 op names, all 38 HARD + 1 SOFT + 1 WARN governor check names/semantics from ADR-0001/0002/0003 unchanged). No new op, no new governor check, no removed check.

## Context

By the time of this ADR, several pieces of `cloud-itonami-hygiene-access`'s own bespoke internal engines had shared/real counterparts land elsewhere in the fleet: `cloud-itonami/cloud-itonami-regulatory-tracker` (extracted FROM this repo's own `hygaccess.regulatory`, generalized on top of `kotoba.crm.pipeline`), `kotoba-lang/dcs` (a general DCS-as-EDN tag-registry + host-injected `IFieldIO` seam, zero prior consumers anywhere in this fleet), `kotoba-lang/kami-app-hygaccess-plant`'s own real, tested finite-volume CFD mixing-tank solve (previously referenced by NAME ONLY, no code dependency), and `kotoba-lang/crm`'s `kotoba.crm.pipeline` (the same ordered-stage engine the regulatory-tracker library itself is built on). Continuing to hand-roll parallel copies of logic that now has a shared, tested home is the kind of drift this fleet's own "ground truth, not self-report" / reuse discipline exists to prevent. This ADR records swapping the ENGINE under four of this repo's own namespaces for that shared/real infrastructure, plus wiring `hygaccess.advisor/llm-advisor` (previously accepted a `ChatModel` but had no constructor for this workspace's own mandated resolution convention) to a real LLM endpoint via the fleet's `murakumo-main` KV alias.

**Same three hard boundaries as ADR-0003, unchanged, still verified**: no payment/fund-movement code, no real regulatory-agency API client, no real equipment-control code. Everything below is either a SHARED SOFTWARE LIBRARY dependency (dcs, crm, regulatory-tracker — pure data/logic, no I/O, no vendor lock-in) or a REAL LLM text-generation endpoint (produces text proposals `hygaccess.governor` still independently re-verifies, never trusted as-is) or a REAL CFD compute function (pure math, no physical actuation of any equipment).

## Decision

### Decision 1: `hygaccess.regulatory` delegates to `cloud-itonami.regulatory-tracker.core`

Added `io.github.cloud-itonami/cloud-itonami-regulatory-tracker` (`:local/root "../cloud-itonami-regulatory-tracker"`, sibling-checkout convention matching every other dep in this file) to `deps.edn`. `hygaccess.regulatory/transitions`/`valid-transition?`/`consequential-statuses`/`evidence-keys`/`evidence-complete?` now DERIVE from `cloud-itonami.regulatory-tracker.core`'s own `ordered-stages`/`exit-stages`/`next-stages`/`valid-transition?`/`consequential-stages`/`evidence-complete?` rather than a hand-rolled stage table — same public var/fn names, same `:record-regulatory-submission-status` op, same `regulatory-transition-invalid`/`regulatory-evidence-missing` governor check names, zero changes required in `hygaccess.governor`.

**ONE documented, accepted behavior deviation** (the shared library's own actual semantics, verified against its real source and tests, not assumed): `:rejected`/`:withdrawn` are now reachable from ANY non-terminal stage (`:draft`/`:counsel-review`/`:submitted`/`:agency-review`), not only from `:agency-review` as this repo's ADR-0003 original table required. `:approved` is UNCHANGED — still reachable only by walking the full `:draft → :counsel-review → :submitted → :agency-review → :approved` chain. DECISION: ACCEPTED, not layered over with an additional stricter check, because (1) no existing test in this repo ever asserted the stricter behavior (verified by inspection — nothing regresses) and (2) early rejection/withdrawal is itself a realistic outcome this actor's original table simply never modeled, not a rule this domain has independent reason to forbid. Full reasoning recorded in `hygaccess.regulatory`'s own ns docstring.

### Decision 2 + 3: `hygaccess.mes` rewired onto `dcs.ports/IFieldIO`, mixing-homogeneity backed by the real CFD solve

Added `io.github.kotoba-lang/dcs` and `io.github.kotoba-lang/kami-app-hygaccess-plant` to `deps.edn`. The bespoke `MESSource` protocol + `MockMES` defrecord are RETIRED in favor of `dcs.ports/IFieldIO` (host-injected `read-tag`/`write-tag!`, zero prior consumers anywhere in this fleet before this build). The four tags this domain needs (pH, temperature, mixing RPM, mixing-homogeneity-cov-pct) are declared in `dcs.model` terms (`hygaccess.mes/mixing-tank-system`, one `:dcs/area` + four `:ai` `:dcs/tags`) — this domain has no automatic control loop (no PID/alarm requirement), so only the tag-registry (`dcs.model`) + read/write seam (`dcs.ports`) portions of `dcs` are used, not `dcs.execute`'s scan-cycle engine, a legitimate partial adoption.

`hygaccess.mes/mock-plant-io` (a `dcs.ports/IFieldIO` implementation, replaces `mock-mes`) seeds pH/temperature/mixing-RPM with the same documented representative defaults `MockMES` used (11.5 / 28.0 / 120.0), but the mixing-homogeneity tag's read is no longer a hand-picked number: `real-cfd-homogeneity-cov-pct` genuinely INVOKES `kami-app-hygaccess-plant.mixing/run-mixing-scenario` (that repo's own tested finite-volume incompressible-NS + scalar-transport solver) over `kami-app-hygaccess-plant.process/default-tank`/`default-process`, and returns its actual `:mixing-homogeneity-cov-pct` result (observed ~1.83e-5% — a well-converged, well-mixed result, consistent with that repo's own golden test). Because that solve is a deterministic pure function of its fixed default inputs (verified against that repo's own `deterministic-across-repeated-runs` golden test), it is memoized via a `delay` (`hygaccess.mes/cfd-result`, private) — realized AT MOST ONCE per process (~2.5s wall-clock measured on the dev machine: PISO to convergence + 40 scalar-transport ticks on a 24×24 mesh), every subsequent read within that process reuses the cached result. `hygaccess.mes/batch-telemetry-reading` reads through an `IFieldIO` to build the SAME reading shape the retired contract documented; `hygaccess.sim`'s demo now genuinely exercises this path for its `:record-mes-reading` happy-path scenario (previously the demo, like every test, hand-constructed the reading value directly — `hygaccess.mes`'s old `MESSource`/`MockMES` layer was documented but never actually invoked by any code path in this repo).

Same `:record-mes-reading` op, same six governor check names (`mes-reading-batch-not-verified`/`mes-reading-ph-implausible`/`mes-reading-temperature-implausible`/`mes-reading-rpm-implausible`/`mes-reading-homogeneity-implausible`/`mes-reading-homogeneity-mismatch`), same five plausibility-window vars `hygaccess.governor` reads by name — zero changes required in `hygaccess.governor`. Test/demo `:value` maps that hand-construct an MES reading directly (every existing test, to exercise specific HARD-hold branches deterministically, e.g. an implausible pH of 15.0) are UNCHANGED and continue to pass through `hygaccess.advisor`'s existing pass-through logic exactly as before — this rewire only replaces the internal mock reference-implementation layer and adds a genuinely-usable, dcs/CFD-backed alternative construction path, it does not force every caller through it.

### Decision 4: `hygaccess.registry`'s fulfillment-status transitions delegate to `kotoba.crm.pipeline`

Added `io.github.kotoba-lang/crm` to `deps.edn`. `hygaccess.registry/fulfillment-transitions`' core ordered-stage/exit-stage validity now delegates to `kotoba.crm.pipeline/valid-transition?`/`next-stages` (`fulfillment-ordered-stages` `[:pending :packed :shipped :delivered]`, `fulfillment-exit-stages` `#{:cancelled}`) instead of a bespoke hand-rolled table — the SAME technical commons `cloud-itonami.regulatory-tracker.core` (Decision 1) is itself built on.

**Unlike Decision 1, this domain rule is kept STRICT, not relaxed**: `kotoba.crm.pipeline`'s own generic semantics make an exit-stage (`:cancelled`) reachable from ANY non-terminal ordered stage, which alone would also permit `:shipped → :cancelled` (`:shipped` is not itself terminal — it still transitions forward to `:delivered`). `hygaccess.registry/fulfillment-transition-valid?` layers ONE additional domain-specific constraint on top (`:cancelled` valid only from `:pending`/`:packed`) — the exact "a caller ... needs the stricter rule can layer that ADDITIONAL check" pattern `cloud-itonami.regulatory-tracker.core`'s own docs describe as sanctioned. Kept strict here (unlike Decision 1's acceptance of the looser default) because existing test coverage (`fulfillment-transition-cancelled-only-from-pre-shipped-states`) already asserts it, and a dispatched parcel is genuinely a different real-world state than an undispatched order. Same `:update-fulfillment-status` op, same three governor check names (`fulfillment-order-not-found`/`fulfillment-transition-invalid`/`fulfillment-shipment-not-on-file`) — zero changes required in `hygaccess.governor`.

### Decision 5: `hygaccess.advisor/llm-advisor` wired to the `murakumo-main` fleet alias (opt-in, `mock-advisor` remains the safe default)

`hygaccess.advisor/llm-advisor` already accepted any `langchain.model/ChatModel` (unchanged by this ADR). Added `murakumo-chat-model` + `resolve-murakumo-endpoint` (public, pure decision logic, no I/O of its own — `http-fn`/`json-write`/`json-read` are host-injected capabilities, the same posture `langchain.model` itself documents): a real, opt-in `ChatModel` constructor targeting this workspace's fleet-wide `murakumo-main` KV alias convention, resolution order per this workspace's own mandated convention:
1. explicit `:override-endpoint`/`:override-model` (env/arg override, e.g. pointing dev at a local Ollama) — never second-guessed;
2. `murakumo-main` alias resolution (`GET https://api.murakumo.cloud/infer/models/murakumo-main` → `{:endpoint :alias-for}`, then call THAT resolved endpoint directly with `:model (:alias-for ..)`);
3. endpoint-only fallback (the stable `https://api.murakumo.cloud/v1/messages` gateway, `:model` the LITERAL alias string `"murakumo-main"` — the worker resolves it server-side — NEVER a concrete model id baked into this fallback branch).

`model/anthropic-model` is the correct adapter here (not the OpenAI-compatible one) because `api.murakumo.cloud/v1/messages` speaks the Anthropic Messages API shape. `mock-advisor` (unchanged) remains the default everywhere, including every automated test in this repo — `murakumo-chat-model`/`llm-advisor` together are an opt-in alternative, mirroring the SAME "mock-advisor for tests, llm-advisor as the real opt-in path" split `etzhayyim/com-etzhayyim-yakushi`/`etzhayyim/com-etzhayyim-swachh-actor` already establish for this exact pattern.

### Decision 6: Test/lint coverage

`test/hygaccess/mes_test.cljc` (new) covers the dcs.model tag registry, the mock `IFieldIO`'s default-seed + override behavior, the real CFD-backed homogeneity reading (genuinely computed, well-mixed, memoized across repeated calls), and `batch-telemetry-reading`'s read-through shape. `test/hygaccess/advisor_test.cljc` (new) covers `resolve-murakumo-endpoint`'s full resolution-order decision logic with fake in-process `http-fn`s — NONE of these new tests make a live network call or depend on the murakumo gateway actually being reachable. Every PRE-EXISTING test file is UNCHANGED (no test needed editing for the regulatory-tracker/crm.pipeline/dcs/CFD swaps — the governor/store/operation/registry/phase contract tests all exercise `hygaccess.governor`'s own check names/semantics, which this ADR preserves byte-for-byte).

## Consequences

(+) Four bespoke internal engines are now backed by shared, independently-tested libraries (`cloud-itonami-regulatory-tracker`, `dcs`, `crm`) or a real, tested compute function (`kami-app-hygaccess-plant`'s CFD solve) instead of hand-rolled duplicates — less code to maintain in this repo, and improvements to those shared libraries now benefit this actor for free.

(+) The mixing-homogeneity MES reading is now backed by genuine physics (a real finite-volume Navier-Stokes + scalar-transport solve), not a hand-picked stub — the "in a real deployment this number would come from ... a CFD mixing-tank simulation" aspiration ADR-0002/0003 documented is now literally true for this build's own mock, not merely a documented intention.

(+) `hygaccess.advisor/llm-advisor` has a concrete, workspace-convention-compliant real-LLM construction path (`murakumo-chat-model`) for the first time — previously it accepted any `ChatModel` but had no wiring to this fleet's own mandated `murakumo-main` alias resolution.

(-) Task-brief-flagged, accepted trade-off: `hygaccess.regulatory`'s early-exit behavior is now slightly looser than the original ADR-0003 table (Decision 1) — a deliberate, reasoned acceptance of the shared library's own broader default, not an oversight.

(-) `deps.edn` now depends on four additional sibling repos (`cloud-itonami-regulatory-tracker`, `dcs`, `crm`, `kami-app-hygaccess-plant`), each via the same `:local/root` sibling-checkout convention already used for `langgraph`/`langchain` — a standalone fork of this repo now needs five sibling checkouts (or git-coordinate overrides) instead of two. `kami-app-hygaccess-plant` itself transitively pulls `kotoba-lang/nagare` + `kotoba-lang/kami-engine-cae-solver` (via `:git/url`+`:git/sha`, resolved automatically by `tools.deps`, not `:local/root` — no additional sibling checkout needed for those two).

(-) The real CFD solve adds ~2.5s of one-time wall-clock cost the first time `hygaccess.mes/real-cfd-homogeneity-cov-pct` (or anything that reads the homogeneity tag through a fresh process) is called — memoized away for every subsequent call within the same process, but unavoidable on cold start.
