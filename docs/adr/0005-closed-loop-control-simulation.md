# ADR-0005: A real closed-loop control simulation for mixing-homogeneity (PID + ISA-18.2 alarm + real stepwise CFD)

## Status

Accepted. Extends `hygaccess.mes` (ADR-0003/ADR-0004) — replaces the memoized single monolithic CFD call backing the mixing-homogeneity MES reading with a genuine iterative closed control loop. No op name, no governor check name/semantic from ADR-0001/0002/0003 was removed, renamed, or weakened; one new SOFT governor check (40) and two new public `hygaccess.mes` vars/fns are additive.

## Context

ADR-0004 wired `hygaccess.mes`'s mixing-homogeneity MES reading to a REAL finite-volume CFD solve (`kami-app-hygaccess-plant.mixing/run-mixing-scenario`) — a large improvement over a hand-picked stub, but still architecturally a single "run the whole 40-tick scenario, read the final number" call, memoized once per process. That is a real CFD result, but it is not a control LOOP: nothing in that path reads a sensor value mid-run, computes a correction, and feeds it back into the next tick's boundary condition. `kotoba-lang/kami-app-hygaccess-plant` (the sibling repo) added exactly the stepwise API (`mixing/init-state` / `mixing/step` / `mixing/sensor-reading`) this needed, and `kotoba-lang/dcs` already ships real, tested `dcs.pid` (PID algorithm) and `dcs.alarm` (ISA-18.2 alarm state machine) namespaces this repo had declared as a dependency (ADR-0004) but never actually called (`hygaccess.mes`'s own ADR-0004 docstring said as much: "this domain has no automatic control loop of its own (no PID/alarm requirement) ... only the tag-registry + read/write seam portions of `dcs` are used"). This ADR closes that gap for real.

**Same hard boundaries as ADR-0003/0004, unchanged, still verified, restated below as FOUR (one new)**: no payment/fund-movement code, no real regulatory-agency API client, no real equipment-control code, and (new, made explicit by this ADR) **no physical actuation pathway anywhere in this codebase** — this is a real, computed closed-loop control simulation entirely within this software's own digital twin, never intended to connect to real hardware.

## Decision

### Decision 1: `hygaccess.mes/run-homogeneity-control-loop` — the real closed loop

Each iteration: (1) read the current CFD state's sensor summary via `kami-app-hygaccess-plant.mixing/sensor-reading` (current CoV + a flow-derived temperature proxy, honestly named as a proxy — that repo has no energy equation); (2) feed `pv = CoV`, `sp = hygaccess.registry/homogeneity-cov-threshold-pct` (5.0%, this repo's own already-registered GMP acceptance threshold, unchanged) into `dcs.pid/step` (`hygaccess.mes/homogeneity-pid-tuning`) to compute a candidate agitator RPM setpoint, clamped to `agitator-rpm-setpoint-actuator-limits` ([10.0, 120.0] RPM — deliberately narrower than the wider `mixing-rpm-plausible-range` fabricated-data-detection window, same "two different windows for two different purposes" pattern `homogeneity-cov-physical-range-pct` vs. `homogeneity-cov-threshold-pct` already established); (3) run one ISA-18.2 scan-cycle (`dcs.alarm/step`, via `evaluate-alarms`) against pH/temperature/the currently-commanded RPM's own plausibility windows (`mixing-tank-system` now also registers six `:dcs/alarms`, a HI/LO pair per tag, and one `:dcs/loop` for the PID, via `dcs.model`'s own builder API) — if ANY is active, OVERRIDE the PID's candidate with `alarm-override-safe-rpm-setpoint` (20.0 RPM — a documented, deliberately non-zero minimum-safe-agitation value: stopping the agitator entirely risks the NaOCl/water charge settling/stratifying while the fault is unresolved, a different and not obviously safer failure mode); (4) apply whichever command won to genuinely advance the CFD's own next tick via `kami-app-hygaccess-plant.mixing/step` — the real boundary-condition update Repo 1's stepwise API exists for; (5) repeat until the CoV is under threshold or `control-loop-max-iterations` (40, matching `mixing/init-state`'s own default `scalar-steps` — never simulating past the batch's own 90-simulated-second mixing window) is hit. Never an unbounded loop.

`dcs.pid/step`'s `error = sp - pv` formula has no reverse/direct-acting toggle; since raising RPM LOWERS CoV (the opposite sign relationship a direct-acting loop assumes — verified for real in `kami-app-hygaccess-plant`'s own `higher-rpm-mixes-faster-than-lower-rpm` test), this loop implements reverse-acting control the standard real-DCS way: NEGATIVE-signed PID gains (`homogeneity-pid-tuning`). Full reasoning for every representative constant (actuator limits, safe-state RPM, gains, iteration bound, alarm deadbands) is documented at each var's own definition in `hygaccess.mes`, per this repo's established discipline.

### Decision 2: `real-cfd-homogeneity-cov-pct` now reads the loop's final trace entry, not a monolithic solve's final tick

`hygaccess.mes/control-loop-result` (a `delay`, replacing the retired `cfd-result`) memoizes `run-homogeneity-control-loop`'s full result AT MOST ONCE per process — same memoization discipline as before, same justification (deterministic pure function of fixed default inputs). `real-cfd-homogeneity-cov-pct` now returns that trace's `:final-cov`. **Behavior change, expected and accepted**: because the loop terminates as soon as CoV first crosses under the 5.0% threshold (a real controller's own correct behavior — it stops driving harder once in spec), the default memoized reading now lands somewhere under 5.0%, not reliably under 1.0% the way the old monolithic 40-tick-to-near-zero run did. `mes_test.cljc`'s `real-cfd-homogeneity-is-genuinely-computed-not-a-stub` test was updated to assert the actual domain requirement (in spec, genuinely computed, never the old hand-picked 2.5) instead of the old mechanism-specific `< cov 1.0` fact.

### Decision 3: control-loop-alarm visibility, independently re-derived — new governor check 40 (SOFT escalation, not a HARD block)

A batch/reading whose real closed-loop trace fired an alarm override must never silently look identical to one that converged cleanly under normal PID control. `hygaccess.mes/batch-telemetry-reading` gains `:control-loop-alarm-triggered?` (sourced DIRECTLY from `control-loop-alarm-triggered?`, the SAME cached trace the homogeneity CoV comes from — deliberately NOT routed through `io`'s overridable tag map like the other four fields, since it is meta-information about how the number was derived, not itself a plant instrument tag; a homogeneity-tag override cannot make an alarm-triggered batch look clean). `hygaccess.governor` gains `control-loop-alarm-stakes?`, an INDEPENDENT ground-truth re-derivation (for `:record-mes-reading`, the proposal's own `:value`; for `:log-production-batch`, the EFFECTIVE `:ipqc`) that forces `stakes?` (and therefore `:escalate?`) true whenever `:control-loop-alarm-triggered?` is true — REGARDLESS of the proposal's own self-reported `:stake`, the same "never taken on the advisor's self-report" discipline every HARD check in this file already applies, now extended to a SOFT escalation gate. `governor/stake-for` and `hygaccess.advisor`'s `record-mes-reading` builder ALSO derive `:coordination/control-loop-alarm-triggered` (added to `high-stakes`) for a well-behaved advisor, but the independent re-derivation is the actual enforcement boundary — a forged/omitted `:stake` cannot suppress it.

**Genuine judgment call** (documented per this repo's own discipline of writing down the reasoning behind ambiguous decisions, not guessing silently): SOFT escalation, not a HARD block. An alarm-overridden batch still physically converged in spec by the time mixing finished — the safe-state agitation setpoint was demonstrably sufficient to reach threshold within the iteration bound (verified empirically: `alarm-triggered-run-forces-safe-state-and-still-terminates-safely` in `mes_test.cljc` shows CoV still strictly improving and converging under the forced-safe 20.0 RPM override) — so it is not itself a violation warranting an automatic HOLD. It IS grave enough that a human go-to-market/QA coordinator must independently see and decide, matching this actor's own established "ground truth over self-report, escalate on ambiguity" posture and its existing SOFT confidence/high-stakes gate's own "ask a human, they may approve" pattern (check 39) rather than a silent pass-through. `:record-mes-reading` is normally phase-3 `:auto`-eligible (auto-commits when clean) — this check gives it real teeth: an alarm-triggered reading no longer auto-commits, it is interrupted for human approval exactly like a HARD-hold-adjacent op.

### Decision 4: the fourth hard boundary, made explicit — no physical actuation pathway anywhere

Stated as plainly and prominently as this repo's existing no-payment/no-real-filing statements (README.md "What this actor does NOT do" / "The three hard boundaries, restated", now four): **this is a real, computed, closed-loop control simulation — sensor read → PID compute → command → CFD state update, iterated — entirely within this software's own digital twin. No GPIO, no serial, no Modbus, no OPC-UA, no PLC client, no equipment-control code of any kind exists anywhere in this codebase or its `kami-app-hygaccess-plant`/`dcs` dependencies, and none is intended.** "Closed-loop" here means the next CFD tick's boundary condition is a real function of the previous tick's simulated state and a genuinely computed command — not that anything physical is being driven.

## Consequences

(+) The mixing-homogeneity MES reading is now backed by a genuine closed control loop (real PID computing real numbers from a real, iteratively-advancing CFD state), not one memoized monolithic solve's own final tick — the "sensor read → PID compute → command → CFD state update, iterated" aspiration is now literally true, not merely a documented intention.

(+) `kotoba-lang/dcs`'s `dcs.pid`/`dcs.alarm` namespaces (declared as a dependency since ADR-0004, never actually called) are now genuinely exercised — the "no PID/alarm requirement" framing in that ADR is superseded for the mixing-homogeneity domain specifically.

(+) A batch/reading that hit a real alarm override during mixing is now independently visible and escalates, closing a gap the "ground truth, not self-report" discipline would otherwise have left silently unaddressed.

(-) Accepted, documented behavior change: `real-cfd-homogeneity-cov-pct`'s default reading is no longer reliably `< 1.0%` (see Decision 2) — `mes_test.cljc` was updated accordingly; no other file depended on that specific numeric fact.

(-) The real closed loop costs more wall-clock than the old single monolithic call (multiple warm-started PISO re-converges instead of one from-rest converge) — still memoized to ONCE per process; measured ~11s cold-start on the default 24×24 mesh on the dev machine (up from ~2.5s), amortized away for every subsequent read within the same process exactly as before.

- All op names, all pre-ADR-0005 governor check names/semantics unchanged — verified by inspection (only additive changes to `hygaccess.governor.cljc`: `high-stakes` gains one member, `stake-for` gains one `case` branch, `check`'s `stakes?` gains one independent `or` term, one new private fn) and by every pre-existing governor-contract/operation/store-contract/phase/registry test passing unmodified.
- No payment/fund-movement, real-agency-filing, or real-equipment-control code was added — `dcs.pid`/`dcs.alarm` are pure computation (no I/O of their own), `kami-app-hygaccess-plant.mixing/step` is pure math over an in-memory CFD state, and this ADR's Decision 4 states the resulting boundary explicitly.
